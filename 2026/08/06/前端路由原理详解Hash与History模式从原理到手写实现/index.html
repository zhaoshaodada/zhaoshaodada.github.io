什么是前端路由，为什么需要它

在传统的多页应用（MPA）时代，页面跳转完全依赖服务端：每次点击链接，浏览器向服务器发起一次全新的 HTTP 请求，服务器返回一个完整的 HTML 文档，浏览器再重新加载整页。这种方式简单可靠，但每次跳转都要经历”白屏 → 请求 → 重新渲染”的全过程，体验割裂，也无法支撑复杂的交互逻辑。

单页应用（SPA）改变了这一范式：整个应用只加载一个 HTML 骨架，后续的”页面切换”全部在前端完成，通过 JavaScript 动态替换页面内容。于是问题来了——既然页面没有真正刷新，浏览器地址栏的 URL 又该如何变化？用户点击后退按钮时，又该如何回到上一个”页面”？

这就是前端路由要解决的核心问题：在不触发整页刷新的前提下，让 URL 与页面视图保持同步，并正确响应浏览器的前进/后退操作。

前端路由的本质，是劫持 URL 的变化，阻止浏览器默认的整页跳转，转而由 JavaScript 根据新的 URL 渲染对应的视图。要实现这一点，浏览器提供了两套机制：基于 location.hash 的 Hash 模式，以及基于 HTML5 History API 的 History 模式。

Hash 模式：以 # 为锚

URL 中 # 后面的部分称为 hash（片段标识符），最初的设计意图是定位页面内的某个锚点。hash 有一个关键特性：它的变化不会触发浏览器向服务器发起请求，也不会导致页面重新加载，只会触发 hashchange 事件。这正是前端路由梦寐以求的能力。

Hash 模式的优点显而易见：兼容性极好（IE8 就支持 hashchange），且无需服务端做任何配合——因为 # 之后的内容压根不会发送给服务器。它的缺点同样明显：URL 里多了一个 #，不够美观；同时由于 # 后内容不参与服务端请求，对 SEO 不够友好（尽管现代爬虫已有所改进，但仍是隐患）。

History 模式：HTML5 的优雅方案

HTML5 引入了 History API，赋予 JavaScript 操作浏览器历史记录的能力，其中最重要的两个方法：

  • history.pushState(state, title, url)：向历史记录栈中压入一条新记录，并更新地址栏 URL，但不会发起请求、不会刷新页面。
  • history.replaceState(state, title, url)：替换当前记录，不会新增历史条目。

History 模式最大的优势是 URL 干净、对 SEO 友好，契合现代 Web 应用的审美与规范。但它有一个不可忽视的代价：需要服务端配合。因为用户可能直接在地址栏输入或刷新 /user/42 这个 URL，此时浏览器会真的向服务器请求这个路径，而服务端并没有对应的资源，于是返回 404。这就要求服务端做”兜底”处理——对所有非静态资源的请求统一返回 index.html，把路由交还给前端。

Hash 与 History 模式对比

两种模式各有取舍，选型时需结合项目实际情况：

维度 Hash 模式 History 模式
URL 外观 带 #，如 /#/user 干净，如 /user
服务端配置 无需配置 需配置回退到 index.html
SEO 友好度 较差（# 后内容不参与请求） 好
兼容性 极佳（IE8+） 良好（IE10+，现代浏览器无碍）
刷新行为 不会 404 未配置服务端会 404
实现复杂度 低 略高

经验法则：对 SEO 有要求的对外站点、后台管理系统、需要干净 URL 的现代应用，优先选 History 模式；对兼容性要求苛刻、或不想折腾服务端配置的场景，Hash 模式是稳妥之选。 Vue Router 默认就是 History 模式，React Router 同样推荐 createBrowserRouter。

手写一个 Mini-Router

理解了原理，我们来亲手实现一个框架无关的迷你路由器，它将支持：路由表注册、动态参数解析（如 /user/:id）、查询字符串解析、事件驱动的视图更新，以及 404 兜底。

设计思路

  1. 路由表：用一个 Map 存储路径与处理函数的映射。
  2. 路径编译：把 /user/:id 这类动态路径编译成正则表达式，并记录参数名，便于后续从 URL 中提取实参。
  3. URL 解析：从 location 中取出当前路径与查询串，拆分处理。
  4. 跳转：封装 push，根据模式调用 location.hash 或 history.pushState，并手动触发渲染。
  5. 事件监听：Hash 模式监听 hashchange，History 模式监听 popstate，并在初始化时手动触发一次。

常见坑与最佳实践

坑一：History 模式刷新 404。 这是最经典的新手陷阱。原因就是服务端没有配置回退，请求 /user/42 时找不到对应资源。解决办法即上文的服务器配置，缺一不可。

坑二：pushState 后视图不更新。 因为 pushState 本身不派发事件。务必在调用 pushState 后手动执行渲染逻辑（如示例中 push 方法内的 this._handle()）。popstate 只在前进/后退时触发，不要指望它能覆盖 pushState 的场景。

坑三：动态参数未解码。 URL 中的参数可能被编码（如中文、特殊字符），提取后必须用 decodeURIComponent 解码，否则会出现乱码或匹配失败。示例代码已做处理。

坑四：链接的默认跳转未拦截。 如果不拦截 <a> 标签的默认行为，浏览器会发起整页请求，前端路由形同虚设。给需要前端路由的链接统一加标记（如 data-router 属性）并用事件委托拦截，是简洁可靠的做法。

坑五：路由懒加载与首屏性能。 路由表变大后，把所有页面组件打包进主 bundle 会拖慢首屏。配合动态 import() 实现按需加载，能显著提升加载性能：

总结

前端路由是单页应用的基石，理解它的原理远比记住某个框架的 API 更有价值。Hash 模式借助 # 的天然特性，简单而兼容性好；History 模式借助 HTML5 API，URL 干净、对 SEO 友好，但需要服务端配合。两者的本质都是劫持 URL 变化、阻止整页刷新、由 JS 驱动视图更新。

通过手写 Mini-Router，我们可以看清路由守卫、动态参数、懒加载这些框架特性的底层落点——它们都建立在 hashchange/popstate 事件与 pushState 这几个原语之上。下次再使用 Vue Router 或 React Router 时，不妨想想它内部正在调用哪一个原生 API，你会发现所谓”框架魔法”，不过是把这些原语封装得更优雅、更完备罢了。
