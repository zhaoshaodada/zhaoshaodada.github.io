用 CSS 容器查询（Container Queries）构建真正响应容器的组件

发表于2026-10-31|更新于2026-10-31|前端
|浏览量:

引言

我们写了无数「响应式组件」，但仔细想会发现一个矛盾：媒体查询（Media Queries）判断的是视口（viewport）宽度，而不是组件自身所在容器的宽度。同一个卡片组件，放在侧边栏的窄槽和放在主内容区的宽槽里，它只会盯着浏览器窗口做同一套判断。结果就是：组件无法真正「自适应其所在位置」，复用越深，布局越乱。

CSS 容器查询（Container Queries）正是为解决这个问题而生：它让元素根据最近的祖先容器的尺寸来做样式分支，把「响应式」的粒度从页面降到了组件。本文用一个可运行的卡片组件，讲清原理与落地。

原理

容器查询分两步：

  1. 用 container-type 把一个元素声明为「查询容器」，它会建立尺寸包含（containment），供后代查询。
    • container-type: inline-size：只建立横向（inline）尺寸包含，最常用，子元素仍可自由决定高度。
    • container-type: size：同时约束横纵尺寸，要求容器本身有确定尺寸，否则会塌陷为 0。
  2. 后代用 @container 规则针对该容器断点生效，语法与媒体查询几乎一致。

可选 container-name 给容器命名，多个嵌套容器时用 @container card (min-width: 400px) 精确指定目标。

常见坑

  1. 尺寸包含导致的塌陷：container-type: size 会让容器脱离内容尺寸，如果父级没给确定高度，容器会塌成 0 高度。绝大多数场景用 inline-size 即可，不要无脑用 size。

  2. 查的是「最近容器」：@container 命中的是最近的、被声明了 container-type 的祖先。如果中间多套了一层没声明容器的 wrapper，查询会向上「跳级」，容易排查时一头雾水。

  3. 与媒体查询职责混淆：容器查询管「组件相对容器」，媒体查询管「页面相对视口」。同一维度既用媒体查询又用容器查询做相反判断，会出现相互打架的样式。建议：页面级断点用媒体查询，组件级用容器查询。

  4. 容器单位：cqw（容器宽度的 1%）、cqi（inline 尺寸 1%）等单位很方便，但注意老浏览器需降级处理，必要时用 @supports (container-type: inline-size) 做特性检测。

小结

容器查询把「响应式」的控制权从视口交还给组件本身，是构建可复用、自适应用户界面组件的关键能力。记住三件事：用 container-type: inline-size 声明容器、@container 写断点、避免与媒体查询在同类项上冲突。下次再写卡片、列表、侧边组件时，先问一句——它要响应的是视口，还是它的容器？
