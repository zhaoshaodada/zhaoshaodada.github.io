深入理解 JavaScript 事件循环：宏任务、微任务与渲染时机

引言

JavaScript 在设计之初就被定为单线程语言：同一时刻只能执行一段代码。这避免了多线程下共享状态的复杂竞态问题，但也带来一个疑问——为什么单线程的 JS 还能处理 AJAX、定时器、用户点击这些”并发”事情而不卡死？答案就是事件循环（Event Loop）。理解它，是写好异步代码、定位”为什么先打印了这个而不是那个”类问题的前提。

原理

浏览器的事件循环维护两个核心队列：

  • 宏任务队列（Macrotask）：script 整体代码、setTimeout、setInterval、I/O、UI 事件、requestAnimationFrame（在多数实现中归为渲染前 task）等。
  • 微任务队列（Microtask）：Promise 的 then/catch/finally、queueMicrotask、MutationObserver 等。

一次循环的执行顺序是：

  1. 执行一个宏任务（最初是整段 script）。
  2. 该宏任务执行完后，清空所有微任务（微任务中产生的微任务会继续排队清空，直到队列为空）。
  3. 如果需要，浏览器执行渲染（取帧、绘制）。
  4. 取下一个宏任务，回到第 1 步。

关键点在于：每一个宏任务结束后，都会先把微任务队列彻底清空，才轮到下一个宏任务。这就解释了为什么 Promise 总是”插队”在 setTimeout 之前。

常见坑

  1. 误以为 setTimeout(fn, 0) 是”立刻”执行。 它只是尽快排入宏任务队列，但必须等当前宏任务及其产生的所有微任务清空后才能执行，实际延迟往往大于 0。

  2. 在微任务里无限循环会饿死宏任务。 因为微任务队列必须清空才会进入下一轮，若在 then 中不断 queueMicrotask 自己，页面将永远无法渲染、无法响应点击。宏任务则不会，每个宏任务之间浏览器有机会渲染。

  3. Promise 构造函数里的代码是同步的。 new Promise((resolve) => { console.log('sync') }) 中的函数体会立即执行，只有 then 回调才是微任务，别把重计算误放进构造体期待它被”异步掉”。

  4. async/await 本质也是微任务。 await 之后的代码等价于 Promise.then，同样受微任务清空规则约束，不会自动让出给宏任务。

小结

事件循环的核心就一句话：一个宏任务 → 清空全部微任务 → 可能渲染 → 下一个宏任务。掌握宏任务与微任务的边界，就能准确预测异步代码的执行顺序，也能合理利用 queueMicrotask 与 requestAnimationFrame 把逻辑调度得既正确又流畅。下次遇到”明明先写的 setTimeout 却后打印”的疑惑，先问一句：中间是不是被微任务插队了？
