Vite 插件实战：从零写一个自动注入构建信息的插件

发表于2026-11-09|更新于2026-11-09|前端
|浏览量:

引言

线上出现问题时，最尴尬的场景之一是：你不知道当前运行的代码对应哪个版本、哪次提交。在 CICD 流程之外，我们完全可以用一个不到 50 行的 Vite 插件，在每次构建时把版本号、Git 提交哈希、构建时间自动打包进产物，运行时随时读取。本文带你从零写一个「构建信息注入插件」，并理解它背后的插件机制。

原理

Vite 插件本质是一个对象，通过暴露生命周期钩子介入构建流程。我们用到两个核心组合：

  • configResolved：配置解析完成后触发，可拿到最终的 root、command 等信息，用来确定项目根路径。
  • resolveId 与 load：这对组合实现「虚拟模块」。当代码 import 一个并不真实存在的路径（如 virtual:build-info）时，resolveId 拦截并返回虚拟 id，load 返回该模块的具体内容，于是我们就能把动态生成的字符串当成普通 ES 模块导入。

构建信息来自 package.json 的 version 字段，以及通过 child_process 执行 git rev-parse HEAD 得到的提交哈希。运行时通过普通 import 拿到，无需任何手动维护。

常见坑

  1. 虚拟模块 id 必须以 \0 前缀解析。\0 是 Vite/Rollup 约定的内部标记，用来避免与真实文件路径冲突；如果只在 resolveId 里返回普通字符串，后续会被当成真实文件而报错。
  2. Git 哈希在 CI 的浅克隆（shallow clone）环境里可能无法获取，或者当前目录根本不是 git 仓库时 execSync 会直接抛异常。必须用 try/catch 兜底，否则一次构建失败会拖垮整个发布。
  3. 不要把 load 里读取的信息缓存到模块顶层。构建时间这类值每次都应重新计算，放在闭包中每次 load 时求值才准确。
  4. 开发服务器（vite）下每次热更新都会重新执行 load，适合调试；若只想在生产构建注入，可在 configResolved 中判断 command === 'build' 再决定是否填充数据。

小结

十几行钩子代码，就把「版本 / 提交 / 时间」这类易变信息自动化进产物，排查问题时一眼就能确认当前运行的是什么。掌握 resolveId 加 load 的虚拟模块套路后，还能用它做环境变量注入、多页应用路由表自动生成等更多事情。建议把它作为团队基建的标配，再配合页面上的「关于」入口展示出来，问题定位效率会明显提升。
