用虚拟列表（Virtual List）渲染十万条数据：前端长列表性能优化实战

发表于2026-11-07|更新于2026-11-07|前端
|浏览量:

引言

列表是前端最常见的交互形态。几百条数据时，一个 v-for 或 map 直接渲染毫无压力。但业务一旦膨胀——日志流、商品池、通讯录、工单列表——数据量冲到一万、十万甚至更多，把全部节点塞进 DOM 的后果是：首屏白屏数秒、滚动掉帧、内存飙升，低端机直接卡死。

问题的根因不在数据本身，而在 DOM 节点数量。浏览器为每个节点维护布局、绘制与事件开销，十万条 <div> 意味着十万个需要参与渲染树与重排的节点。虚拟列表（Virtual List）的核心思想只有一句话：无论数据有多少，永远只渲染视口内（及少量缓冲）的那若干个节点。

原理

虚拟列表在 DOM 结构上做三层切分：

  1. 视口容器（viewport）：固定高度、开启 overflow-y: auto 的可滚动区域，用户实际看到的部分。
  2. 占位撑高层（spacer）：一个高度为「总数据量 × 单行高度」的空元素，它的唯一作用是让滚动条比例正确，制造出“列表很长”的假象。
  3. 内容渲染层（content）：真正挂载可见节点的容器，通过 transform: translateY() 向上偏移，使自己始终对齐当前可见区间。

当用户滚动，我们根据 scrollTop 算出当前可见区间的起点下标 start = Math.floor(scrollTop / itemHeight)，再结合容器高度算出 end = start + visibleCount + buffer。只截取 [start, end) 这段数据渲染，并用 start * itemHeight 作为偏移量把内容层推到正确位置。这样无论底层有 100 条还是 100000 条，DOM 里始终只有几十个节点。

常见坑

  1. 行高必须可计算。上面的实现依赖「固定行高」才能用乘法直接定位。itemHeight 一旦被内容撑开（比如某行折行），偏移就会错位、滚动跳动。动态高度场景必须预先测量并缓存每行的真实高度，再配合二分查找定位起始下标。

  2. 缓冲区不能省。不加 BUFFER 时，极速滚动会因「滚到哪才渲染哪」出现白屏闪烁，缓冲行就是为视觉连续性买的保险。

  3. 滚动事件要节流。直接在 scroll 里 innerHTML 重建会每像素触发一次重排。用 requestAnimationFrame 合并到下一帧渲染，是性价比最高的优化。

  4. 事件用委托，别逐节点绑定。既然节点在不停销毁重建，给每个 .row 绑 click 既浪费又易失效。把监听挂在 #content 上，用 e.target 取数据下标才是正解。

  5. 只渲染可见区，但数据筛选/搜索在外层。虚拟列表解决的是“渲染”问题，卡顿若来自 filter 十万次的纯计算，应先用索引或 Web Worker 处理数据层。

小结

虚拟列表用「以时间换空间」的思路，把 DOM 节点数量从数据规模解耦到视口规模，是处理超长列表最稳妥的性能方案。生产环境可以直接上成熟库（vue-virtual-scroller、react-window、@tanstack/virtual），但理解了上面的 scrollTop → start/end → translateY 三步推导，你就能在任何框架、甚至原生项目里自己撸一个，并在动态高度、横向列表、网格瀑布等变体上游刃有余。
