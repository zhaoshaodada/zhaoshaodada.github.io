Cesium实例化渲染详解：同模型万级批量绘制方案

发表于2026-07-31|更新于2026-08-01|技术分享
|浏览量:

痛点：同模型大量复制的性能困境

在 Cesium 开发过程中，我们常会为添加一整片森林、一排排路灯、沿山脊排开的风机感到苦恼，不是模型不好找而是添加这些模型的量太大。这些东西都是同一个模型复制成千上万份。如果一个个 Entity 去加，浏览器分分钟卡死。

instance 实例化渲染，就是为解决”同一个模型画很多次”这件事做的。下面说清楚它到底能干什么，再详细讲解实例化渲染在高版本的 Cesium 中如何实现。

这个功能能拿来干嘛

凡是”同一个模型，出现很多次”的场景，都该用实例化。几种典型用途：

  • 种树 / 森林：一个树的 GLB，往一片山上铺几万棵。每棵位置不同、朝向随机，但模型只加载一次。
  • 工程工地：塔吊、集装箱、施工车辆，按实际坐标批量摆放，模拟现场布局。
  • 电力线路：电线杆、铁塔沿路径等距排开，几百根一根根画。
  • 城市家具：路灯、消防栓、长椅、垃圾桶，整条街整条街地铺。
  • 车队 / 设备分布：demo 默认就是 100 辆消防车 10×10 方阵，模拟车队或装备到位情况。
  • 军事 / 态势标绘：装备、阵地、雷达站的批量摆放。

共同点是模型共用、变换各异。这正是 GPU 实例化（instancing）的拿手好戏。

底层是怎么实现的

只加载一个 GLB，靠 GPU 把它画成 N 份，每份位置、朝向、缩放各不相同。关键靠三样东西。

一、用一个局部坐标系，绕开精度问题

地球坐标（ECEF）的数字是百万米量级，而模型顶点是米级。两个量级的数在 vertex shader 里相乘，float32 的精度撑不住，模型就开始抖动变形。

之后每个实例的 modelMatrix 存的是相对这个中心的局部坐标，都是小数字，精度稳了。

二、把 N 个变换矩阵塞进一张纹理

GPU 实例化要每个实例喂一个变换矩阵。Cesium 没直接给 per-instance uniform，这里用了个常见做法：把所有矩阵打包成一张纹理，shader 里按实例号去取。

一张纹理装下全部变换，加一个实例只是往纹理里多写一列，不用碰模型本身。

几个细节值得说

为什么默认随机朝向

buildModelMatrixFromInstance 里有个约定：angle === undefined 才随机 0 到 360 度，传了 null 或数字就用那个值。种树、撒建筑时每棵朝向不一样才自然，全部正着放反而假。代码注释把这层逻辑写得很明白。

视锥裁剪

摄像机背面的实例不该画。_frustumCulled 每帧拿每个实例的包围球和视锥求交，只把可见的重新打包成一张小纹理喂给 shader。转动相机时背面那些不参与渲染，省下不少开销。demo 默认开了 enableFrustumCulling: true。

怎么点中某一个

实例化后所有实例是”一坨”，普通 picking 失效。解决办法是给每个实例发一个唯一 pickId 颜色，存进 id 纹理；fragment shader 把这个颜色画到片元上，鼠标点哪里就读那个像素的颜色，反查到对应实例。”高亮”就是拿这个 id 和某个目标 id 比，对上了就涂成亮黄加自发光。

局部坐标这个选择还有个好处

拦 draw command 时，代码把 cmd._modelMatrix 强行设成 centerMatrix，每个实例真正的变换是靠矩阵纹理在 shader 内完成的。这样模型本身始终待在局部坐标系里，不用每个实例单独算一遍完整的 ECEF 变换。

小结

实例化绘制要解决的是”同模型、高复用、强交互”的渲染。它把变换塞进纹理，绕开了 per-instance uniform 的限制；靠 instanceCount 把一次 draw call 复制成 N 份；用视锥裁剪和包围盒保住帧率；最后用 id 纹理把”点中哪一个”这件事捡了回来。

拿去种树、摆电塔、堆集装箱都合适。换模型只改 GLB 地址，要多少实例往 instances 数组里塞坐标就行。
